# 학습 노트 — JWT 인증과 Spring Security

- 작성일: 2026-08-19 / API-01·02, JWT 필터 구현하며 정리
- 관련: D-018(인증 방식), docs/dev/04-API-명세.md

## 큰 그림 — 모든 요청은 검문소를 지난다

```
앱의 요청 → [JwtAuthFilter: 신분 확인] → [SecurityConfig 규칙: 통과/차단 판정] → Controller → Service → DB
```

## 등장인물 5명 (역할은 각자 하나씩)

| 클래스 | 역할 | 비유 |
| :---- | :---- | :---- |
| SecurityConfig | 경로별 통행 규칙 (permitAll / authenticated), 필터 배치(addFilterBefore) | 규칙표 |
| PasswordEncoder | encode(가입: 해시 생성) / matches(로그인: 다시 해시해서 대조) | 금고 기술자 |
| JwtProvider | createToken(발급) / parseUserId(검증, 이상하면 null) | 손목 밴드 발급기 |
| JwtAuthFilter | 매 요청 Authorization 헤더 검사 → SecurityContextHolder에 userId 기록. **차단은 안 함(기록만)** — 판정은 규칙표의 몫 | 검문소 직원 |
| OpenApiConfig | Swagger 화면에 Authorize(Bearer) 버튼 표시. 서버 동작과 무관 | 문서에 자물쇠 그리기 |

## 두 개의 흐름

1. **로그인(발급)**: findByEmail 조회 → matches로 대조 → createToken → 앱이 토큰 보관
2. **이후 모든 요청(검증)**: 앱이 `Authorization: Bearer {토큰}` 헤더에 실음 → 필터 검사·기록 → 규칙표 판정 → Controller

서버는 아무것도 기억하지 않는다(무상태). 세션 방식(서버가 회원명부 보관, 쿠키는 열쇠 번호)과의 근본 차이 —
JWT는 "위조 불가 도장이 찍힌 손목 밴드"로, 명부 없이 밴드만 보고 통과시킨다.

## 핵심 주의사항

- JWT 페이로드는 **인코딩이지 암호화가 아님** — 누구나 열어볼 수 있으니 userId만 넣고 비밀은 절대 넣지 않는다
- 비밀번호는 "복호화해서 비교"가 아니라 "**다시 해시해서 비교**"(matches). DB에는 BCrypt 해시만 저장 (D-018)
- 로그인 실패 시 이메일/비밀번호 중 뭐가 틀렸는지 알려주지 않는다 (계정 존재 여부 노출 방지)
- 예외 발생 시 Spring이 내부적으로 `/error`로 이동 → 이 경로도 permitAll 필요 (안 하면 409가 403으로 덮임)
- 시크릿 키·설정값은 application-local.yml(git 제외)에만. yml은 들여쓰기가 곧 주소

## 꼭 기억할 구문 5개

```kotlin
// 1. 주입은 항상 "클래스명 옆 소괄호 안" (생성자)
class AuthService(private val userRepository: UserRepository) { }

// 2. yml 값 주입 — Kotlin에서는 $ 앞에 반드시 백슬래시
@Value("\${jwt.secret}")

// 3. null 3형제
val nickname: String?                  // 선언: null 허용 타입
val name = request.nickname ?: email   // 엘비스: null이면 대신 이 값
val id = saved.id!!                    // 단언: null 아님을 내가 보장 (틀리면 즉시 예외)

// 4. "조회 실패 = 예외" 한 문장 패턴 — 모든 조회 API에서 반복됨
val user = userRepository.findByEmail(email)
    ?: throw ResponseStatusException(HttpStatus.UNAUTHORIZED, "...")

// 5. 모든 .kt 파일의 첫 줄은 package 선언 — 붙여넣기가 이 줄을 지우지 않았는지 확인
package com.smartkitchen.backend.auth
```

## 오늘 밟은 함정 (재발 방지)

- build.gradle.kts 수정 후 **Gradle 동기화(코끼리)** 없이 실행 → 이전 클래스패스로 동작
- IntelliJ 프로젝트 창의 .kt 표시 유무는 **표시 규칙**일 뿐 — Rename으로 확장자를 붙이지/떼지 않는다 (Household.kt.kt 사고)
- `@Transactional`은 jakarta가 아니라 `org.springframework.transaction.annotation` 쪽을 import
- HTTP 상태: 201 자원 생성 / 400 요청 자체가 깨짐(JSON 오류) / 401 인증 실패 / 403 권한 없음(토큰 없이 보호 경로) / 409 중복
