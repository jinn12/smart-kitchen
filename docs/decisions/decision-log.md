## D-001. 1차 타겟은 30\~40대 주부로 한정

**배경** 초기 구상에서 타겟을 "30\~40대 주부"와 "1인 가구 직장인" 두 그룹으로 잡았다.

**검토한 대안**

| 대안 | 내용 |
| :---- | :---- |
| A | 두 그룹을 모두 대상으로 설계 |
| B | 주부로 한정 |
| C | 1인 가구로 한정 |

**결정** — B (주부로 한정). 1인 가구는 2차 타겟으로 문서에만 남긴다.

**근거**

- 두 그룹의 요구가 상이하다. 주부는 재고 규모가 크고 주 1회 대량 장보기를 하며 반복 메뉴가 많다. 1인 가구는 재고가 적고 "사놓고 썩힘"이 핵심 고통이며 요리 빈도 자체가 낮다.  
- 1인 가구는 요리 빈도가 낮아 레시피·식사계획 기능의 사용률이 구조적으로 낮다. 이 서비스의 순환 구조와 궁합이 맞지 않는다.  
- 개인 프로젝트로서 검증 속도를 확보하려면 타겟을 좁히는 편이 유리하다.

## D-002. 재고 차감은 "예약 후 확정" 방식으로 처리

**배경** 식사 계획을 등록할 때 레시피의 재료만큼 재고를 차감해야 한다. 차감 시점을 언제로 볼 것인가.

**검토한 대안**

| 대안 | 내용 | 문제점 |
| :---- | :---- | :---- |
| A | 계획 등록 시 즉시 차감 | 미래 날짜 계획까지 현재 재고를 깎아 실물과 어긋남 |
| B | 조리 완료 버튼을 눌렀을 때 차감 | 정확하지만 사용자 입력 부담이 크고 이탈 요인이 됨 |
| C | 등록 시 예약(reserve), 날짜 경과 후 자동 확정 | 필드 1개와 배치 작업 1개가 추가됨 |

**결정** — C.

- `Inventory`에 `quantity`(실물 보유량)와 `reserved_quantity`(계획 예약량)를 둔다.  
- 화면 기본 표시와 장보기 부족 판단은 `가용 = quantity - reserved` 기준으로 한다.  
- 계획 날짜가 지나면 배치 작업이 예약분을 실제 차감으로 확정한다.  
- **사용자는 "조리 완료" 버튼을 누르지 않는다.**

**근거**

- 사용자 체감은 A와 동일하다(등록하면 빠진 것처럼 보임). 입력 부담을 늘리지 않는다는 요구를 충족한다.  
- 주 타겟인 주부는 주간 식단을 한 번에 몰아서 등록하는 경우가 많다. A를 택하면 이 시나리오에서 냉장고 화면이 실물과 크게 어긋난다.  
- 실물 수량이 보존되므로 D-003(유통기한 관리)과 충돌하지 않는다.  
- 계획 취소·수정 시 예약분만 되돌리면 되므로 이력 역분개가 필요 없다.  
- 부가 효과: 배치 스케줄러 설계가 포트폴리오 설명 소재가 된다.

## D-003. 유통기한을 MVP에 포함하고, 재고를 배치 단위로 관리

**배경** 유통기한 관리를 MVP에 넣을지, 포트폴리오 버전으로 미룰지.

**검토한 대안**

| 대안 | 내용 |
| :---- | :---- |
| A | MVP 제외. 재고는 식재료당 1행(합계)으로 단순 관리 |
| B | MVP 포함. 재고를 배치(구매 시점) 단위로 관리 |

**결정** — B.

- `InventoryItem`(배치: 수량, 유통기한, 구매일)을 두고 `Inventory`는 집계로 다룬다.  
- 차감 순서는 FEFO(유통기한이 빠른 배치부터)를 적용한다.  
- 배치 지정은 D-002의 확정 시점까지 미룬다(예약 단계에서는 총량만 잡는다).

**근거**

- 재고 관리 앱이 실패하는 주된 이유는 "입력은 귀찮은데 열어볼 이유가 없어서"다. 유통기한 임박 알림은 재방문 동기를 만드는 사실상 유일한 장치다.  
- 합계 방식으로는 유통기한을 표현할 수 없다. 나중에 도입하면 재고 관련 전 로직의 재작성이 필요하다.  
- 대신 다른 영역의 깊이를 줄여 총량을 맞춘다(D-009 참조).

## D-004. 단위는 식재료당 고정, 3종 \+ 선택적 포장 단위

**배경** 레시피는 `두부 100g`인데 장보기는 `두부 1모`, 재고는 `간장 1병`이다. 구매 단위와 사용 단위가 달라 변환 문제가 발생한다.

**검토한 대안**

| 대안 | 내용 |
| :---- | :---- |
| A | 식재료마다 여러 단위 허용 \+ 변환 테이블 |
| B | 식재료당 단위 1개 고정 |
| C | B \+ 표시 전용 포장 단위 추가 |

**결정** — C.

- `unit_type`은 `COUNT(개)` / `WEIGHT(g)` / `VOLUME(ml)` 3종.  
- `package_name`, `package_size`는 선택 입력 (예: 두부 1모 \= 300g).  
- **모든 계산은 `base_unit`으로만 수행하고 포장 단위는 표시 전용으로 제한한다.**  
- 레시피 재료 입력 시 해당 식재료의 단위를 자동 고정 표시한다(수량만 입력).

**근거**

- 단위를 고정하면 변환 로직이 사라진다. g 관리가 번거로운 사용자는 식재료를 `COUNT`로 등록하면 되므로 자유도도 확보된다.  
- 수량·중량 2종으로는 간장·우유·식용유를 담을 수 없어 부피가 반드시 필요하다.  
- 주 타겟이 주부이므로 장보기 화면에서 "두부 300g(1모)" 형태의 표시가 실사용에 중요하다.  
- 계산과 표시를 분리하면 포장 단위를 추가해도 복잡도가 늘지 않는다.

**부가 결정** — 소금·후추·식용유 등 정량 관리가 사실상 불가능한 품목을 위해 `is_trackable` 플래그를 두고 재고 차감 대상에서 제외한다. "간장 잔량 3ml" 같은 표시는 앱 전체의 신뢰도를 떨어뜨린다.

## D-005. Ingredient는 시스템 마스터 \+ 사용자 커스텀 하이브리드

**배경** 식재료 데이터를 사용자가 자유 입력하게 할지, 시스템이 표준 목록을 제공할지.

**검토한 대안**

| 대안 | 내용 | 문제점 |
| :---- | :---- | :---- |
| A | 사용자 자유 입력 | "두부"와 "부침두부"가 별개 식재료로 갈라짐. 오타 누적. AI 표준화의 매핑 대상이 없음 |
| B | 시스템 마스터만 제공 | 목록에 없는 식재료를 등록할 수 없음 |
| C | 마스터 검색 \+ 없으면 직접 추가 | 초기 데이터 구축 비용 발생 |

**결정** — C. 마스터에 `category`, `default_storage`, `default_shelf_life`, `unit_type`, `base_unit`을 포함한다. 커스텀 식재료는 `is_custom = true`와 소유자를 갖는다.

**근거**

- 입력 부담이 크게 줄어든다. "두부" 선택만으로 보관 장소(냉장), 단위(g), 유통기한(+7일)이 자동으로 채워지고 사용자는 수량만 입력한다. 주 타겟에서 이탈을 막는 데 결정적이다.  
- D-007(AI 품목 인식)의 매핑 착지점이 된다. 표준 목록이 없으면 "표준화"라는 개념 자체가 성립하지 않는다.  
- `default_shelf_life`가 D-007의 유통기한 문제를 우회하는 수단이 된다.  
- 초기 데이터 구축(300\~500건)은 하루 규모이며, 데이터 설계 경험 자체가 포트폴리오에 기여한다.

## D-006. 데이터 소유자 축은 user\_id가 아닌 household\_id

**배경** 가족 간 냉장고 공유를 지원할지. 주부 타겟이라면 배우자와의 공유 요구가 발생할 가능성이 높다.

**검토한 대안**

| 대안 | 내용 |
| :---- | :---- |
| A | MVP는 `user_id` 소유. 공유가 필요해지면 그때 전환 |
| B | 처음부터 `household_id` 소유. 공유 UI만 만들지 않음 |

**결정** — B.

- `Household` 테이블을 두고 모든 데이터의 소유자를 `household_id`로 건다.  
- 회원가입 시 개인 Household를 자동 생성한다.  
- **초대·멤버 관리·권한 구분·공유 알림은 MVP에서 만들지 않는다.** UI에 공유의 흔적을 두지 않는다.

**근거**

- 추가 비용은 테이블 1개와 가입 로직 1줄이다.  
- A를 택하면 나중에 냉장고·레시피·식탁·장보기 전 테이블의 소유자 축을 변경하고 모든 조회 쿼리를 수정해야 한다.  
- 확장 가능성만 열어두고 기능은 만들지 않는다는 원칙에 부합한다.

**남은 과제** — 실제 공유 도입 시 어려운 부분은 스키마가 아니라 동시 수정 충돌 처리와 변경 알림이다. 해당 시점에 별도로 다룬다.

## D-007. AI는 사진 기반 품목 인식(VLM)으로, 확장 기능으로 유지

**배경** 초기 구상은 영수증 OCR \+ AI 표준화였다. 이후 "냉장고나 장 봐온 물건을 촬영해 자동 등록"하는 방향으로 변경을 검토했다.

**검토한 대안**

| 대안 | 내용 | 판단 |
| :---- | :---- | :---- |
| A | 고전 객체 탐지(YOLO 등) 학습 | 범용 모델은 한국 식재료를 인식하지 못하고, 직접 학습에는 수천 장의 라벨링 데이터가 필요. 1인 프로젝트로 불가능 |
| B | 멀티모달 LLM(VLM)에 사진을 전달해 품목 목록 추출 | 학습 데이터 불필요, 한국 제품 포장 인식 가능, 결과를 구조화된 형태로 수신 |
| C | 영수증 / 주문내역 캡처 인식 | 정확도가 높고 구현이 쉬우나 냉장고 실사가 불가능 |

**결정** — B를 포트폴리오 v1으로, C를 v2로 한다. AI는 MVP에서 제외하며 Core가 아닌 Extension으로 유지한다.

**세부 결정**

- **유통기한은 사진에서 인식하지 않는다.** 포장 밑면·접합부에 소형 인쇄되어 있어 일반적인 촬영 사진에서는 판독이 불가능하다. 대신 D-005의 `default_shelf_life`로 날짜를 제안하고 사용자가 수정한다.  
- **수량도 자동 인식에 의존하지 않는다.** 기본값 1을 제시하고 사용자가 조정한다. 가려짐·포장·중량 판별 불가 문제가 있다.  
- 사진에서 얻는 정보는 **"무엇이 있는가"로 한정**한다.  
- **AI 결과는 어떤 경우에도 자동 확정하지 않는다.** 신분증 촬영 흐름과 같이 인식 → 사용자 검증 → 등록의 순서를 강제한다. 확신이 낮은 항목은 시각적으로 구분하고 기본 선택을 해제한다.  
- 사용자의 수정 내역을 로그로 남겨 인식 품질 개선의 근거로 삼는다.  
- 냉장고 사진은 주거 공간 정보를 포함하므로 **인식 후 원본을 즉시 폐기**한다.

**근거**

- B는 학습 데이터 없이 즉시 동작하며, 별도 모델 서빙 서버가 불필요해 아키텍처가 단순해진다.  
- C는 정확도가 높지만 이미 냉장고에 있는 식재료를 다룰 수 없다. 두 방식은 경쟁 관계가 아니라 서로 다른 문제를 해결한다.  
- 인식 정확도가 70% 수준이어도 검증 단계가 있으면 서비스는 성립한다. 반대로 자동 확정은 정확도 95%에서도 신뢰를 훼손한다.  
- 문서에 "유통기한 자동 인식"으로 기재하면 실현 불가능한 목표에 개발 시간을 소모하게 된다.

## D-008. 서비스 용어는 "식단" 대신 "식탁"을 사용

**배경** "식단"은 다이어트 서비스의 인상이 강하다.

**결정** — 엔티티명은 일반적인 영문 명칭(`Ingredient`, `Inventory`, `Recipe`, `MealPlan`, `ShoppingList`, `InventoryHistory`)을 사용하고, 화면 라벨은 한국어로 매핑한다.

| Entity | 화면 라벨 |
| :---- | :---- |
| Ingredient | 식재료 |
| Inventory | 냉장고 |
| Recipe | 요리 |
| MealPlan | 식탁 |
| ShoppingList | 장보기 |
| InventoryHistory | 기록 |

**근거 및 유보 사항**

- 브랜드 톤에서 "식탁"은 차별성이 있으나, 탭 라벨로서는 기능이 즉각적으로 전달되지 않는다는 약점이 있다.  
- 하단 탭 라벨만 "식사" 또는 "오늘"로 분리하는 절충안을 검토 가능하다. 사용자 테스트 없이는 확정할 수 없으므로 현 시점에서는 "식탁"으로 진행한다.  
- `Inventory`를 "냉장고"로 부르면 실온 보관 식재료(쌀, 라면 등)가 어색해진다. `StorageLocation`(냉장/냉동/실온) 속성을 두어 냉장고 화면 내에서 구분한다.

## D-009. MVP는 4개 도메인을 모두 포함하되 각각의 깊이를 제한

**배경** 냉장고·요리·식탁·장보기 4개 도메인 전체를 앱스토어 출시까지 완성하는 것은 개인 프로젝트로 부담이 크다. 그러나 순환 구조가 서비스의 정체성이므로 도메인을 제거하면 차별점이 사라진다.

**결정** — 도메인은 유지하고 각 도메인의 기능 깊이를 제한한다.

| 도메인 | MVP 범위 | 제외 |
| :---- | :---- | :---- |
| 요리 | 재료 목록만 | 조리 순서, 사진, 소요 시간 |
| 식탁 | 날짜 \+ 끼니 \+ 레시피 연결 | 영양 정보, 칼로리 |
| 장보기 | 단일 장바구니 | 마트별 분리, 가격 비교 |

여기서 확보한 여력을 유통기한(D-003)과 장보기 완료 → 재고 반영 흐름의 완성도에 투입한다.

## D-010. 부족 재료 처리는 계획 단위로 일괄 안내

**배경** 초기 구상은 재료가 부족할 때 "100g만 사용하시겠습니까? 예 / 아니오"를 묻는 방식이었다.

## D-011. 기술 스택은 Kotlin/Spring Boot + Flutter + PostgreSQL + Lightsail로 확정

**배경** 무료 앱으로 실제 스토어 출시·운영(상용화)이 1순위이고, 이직 포트폴리오가 병행 목표다. 개발자는 1인, 경력은 Java/전자정부프레임워크 기반 웹 개발 5년. 최대 리스크는 (1) 미완성으로 인한 출시 실패, (2) 무료 앱을 지탱해야 하는 운영 비용·유지보수 부담이다.

**검토한 대안**

| 영역 | 대안 | 판단 |
| :---- | :---- | :---- |
| 백엔드 | Supabase(BaaS) | 출시 속도 최고. 배치·비즈니스 로직 제약, 백엔드 포트폴리오로 약함 |
| 백엔드 | NestJS / FastAPI | 생산성 높으나 국내 백엔드 채용 수요가 Spring 대비 적고, 기존 경력과 단절 |
| 백엔드 | Spring Boot + Java 21 | 학습량 최소(신규 요소는 JPA뿐). 언어 전환 신호는 없음 |
| 백엔드 | Spring Boot + Kotlin | Java 경력자에게 러닝커브 낮고, 운영 안정성·채용시장 신호 우위 |
| 앱 | React Native (Expo) | React 경험이 없어 JS/TS + React + RN 3중 학습. 플랫폼별 렌더링 편차 대응 부담 |
| 앱 | Kotlin Multiplatform | 백엔드와 언어 통일 가능하나 iOS 지원 성숙도가 실출시 목표에 리스크 |
| 앱 | Flutter | Dart가 Java와 유사, 자체 렌더링으로 iOS/Android 동일 동작 |
| 인프라 | AWS 정석 (ECS+RDS) | 월 3~5만원대 고정비와 운영 부담이 무료 앱에 과함 |
| 인프라 | 경량 PaaS (Railway 등) | 저비용·간편하나 AWS 경험으로 인정받기 어려움 |
| 인프라 | AWS Lightsail | AWS 이력과 저비용(월 1~2만원)의 절충 |

**결정**

| 영역 | 선택 |
| :---- | :---- |
| 백엔드 | Spring Boot 4 + Kotlin + JPA (프로젝트 생성 시점 최신 안정 4.1.0 — 결정 당시 표기는 3이었으나 3.x OSS 지원 종료로 4.x 확정) |
| DB | PostgreSQL |
| 앱 | Flutter (Dart) |
| 인프라 | AWS Lightsail + Docker + GitHub Actions CI/CD |
| 배치 | Spring `@Scheduled`로 시작, 필요 시 Spring Batch 전환 |
| AI (확장) | 백엔드가 외부 VLM API를 호출하는 프록시 구조. 별도 ML 인프라 없음 |

**근거**

- **Kotlin**: null 안전성이 런타임 NPE를 컴파일 시점에 차단해 1인 운영의 장애 리스크를 줄인다. 코드량 감소는 유지보수 표면적 감소로 직결된다. 국내 서비스 기업 백엔드의 주류 채택 언어로, 전자정부 → Spring Boot + JPA + Kotlin 전환 자체가 이직 서사가 된다. Java 경력자에게 러닝커브가 낮고 AI 도구가 이를 추가로 흡수한다.  
- **Flutter**: 후보 중 유일하게 기존 언어 경험(Java 계열 문법)이 이전된다. 자체 렌더링 엔진으로 플랫폼별 버그가 구조적으로 적어 1인 유지보수 총비용이 최소다. 앱은 심사 대상이 아니라 "출시를 증명하는 클라이언트"이므로 크로스플랫폼 1회 개발이 합리적이다.  
- **PostgreSQL**: FEFO 차감(D-003), 예약 수량(D-002) 등 관계형 로직이 핵심이며 ERD 설계가 문서 로드맵에 포함되어 있다.  
- **Lightsail**: 초기에는 단일 인스턴스에 앱+DB를 컨테이너로 배치해 비용을 고정하고, 사용자 증가 시 RDS 분리를 확장 경로로 남긴다.  
- AI 확장(D-007)은 VLM API 호출만으로 동작하므로 본 스택에 아무것도 추가하지 않는다. MVP의 식재료 마스터(D-005)와 일괄 등록 화면(부록)이 확장 착지점이 된다.

**유보** — 목표 포지션(백엔드 vs 앱)은 출시 후 결정한다. 단, 본 스택은 백엔드 포지션 서사에 유리한 구성이다.

## D-012. 하단 4탭 구조, 시작 탭은 냉장고, 끼니는 3종

**배경** IA 작성을 위해 앱 골격(탭 구성, 시작 화면, 끼니 구분, 설정 위치)의 확정이 필요하다.

**검토한 대안**

| 항목 | 대안 | 판단 |
| :---- | :---- | :---- |
| 탭 구성 | 5탭 (홈 + 4도메인) | 홈 화면 1개가 추가되어 MVP 총량 초과. 홈의 역할이 다른 탭과 중복 |
| 탭 구성 | 4탭 (냉장고/요리/식탁/장보기) | 순환 구조의 4개 도메인이 그대로 탭이 됨 |
| 시작 탭 | 식탁 vs 냉장고 | 재고 중심 정체성과 알림 착지 일관성은 냉장고 우위 |
| 끼니 | 3종 vs 4종(간식 포함) | 간식은 계획성이 낮아 재고 차감 가치가 작음 |
| 설정 | 하단 탭 vs 상단 아이콘 | 설정은 저빈도 기능으로 탭 자리가 아까움 |

**결정**

- 하단 탭은 **냉장고 / 요리 / 식탁 / 장보기** 4탭. 홈 탭 없음.
- 시작 탭은 **냉장고**, 유통기한 푸시 알림 착지점도 냉장고 임박 섹션으로 통일.
- 끼니는 **아침 / 점심 / 저녁** 3종. 간식·야식은 확장 여지로만 남긴다.
- 설정·계정은 상단 앱바 아이콘.

**근거**

- 홈 탭이 하던 역할은 분산 흡수된다 — "오늘 뭐 먹지"는 식탁 탭이 오늘 포커스로 열리는 것으로, "임박 확인"은 냉장고 탭 상단 임박 섹션 + 푸시로. 화면 추가 없이 동일한 가치를 제공한다.
- 주 타겟(주부)의 식사 준비 단위는 세 끼니다.
- 홈/리포트 탭은 확장 지점으로 문서에만 남긴다.

## D-013. 유통기한 임박 정책 — 기준 3일, 매일 요약 푸시, 화면 D-배지

**배경** 임박 기준 일수와 알림 발송 방식을 확정해야 한다. 매일 발송 시 같은 항목으로 최대 4일 연속 알림이 가는 피로도 우려가 있었다.

**검토한 대안**

| 대안 | 내용 | 판단 |
| :---- | :---- | :---- |
| A | 임박 항목이 있는 한 매일 발송 | 리마인드 확실, 구현 단순. 피로도 우려 |
| B | D-3 진입일에만 1회 발송 | 피로 최소. 그날 놓치면 재안내 없음 |
| C | 진입일 + 유통기한 당일 2회 | 절충안 |

**결정** — A.

- 임박 기준은 **유통기한 3일 전(D-3)부터**.
- 임박 또는 만료 항목이 있는 가구에 **매일 09:00 요약 푸시 1건** 발송 (알림 허용자 한정).
- 예약 확정 배치는 매일 00:10.
- **화면 표시 규칙**: 재고 목록에서 임박 항목은 D-3 / D-2 / D-1 배지, 유통기한 경과 항목은 빨간색 "만료" 표시.

**근거**

- 푸시는 허용한 사용자에게만 가므로, 매일 발송의 피로도 리스크는 사용자의 선택으로 완충된다.
- 처리될 때까지 반복 리마인드되는 것이 "폐기 방지"라는 기능 목적에 부합한다.
- 화면 내 D-배지와 만료 표시가 알림 비허용 사용자의 보완 채널이 된다. 앱을 열기만 하면 상태를 즉시 인지할 수 있다.
- 알림 → 오픈 전환율을 측정해 출시 후 발송 정책을 재조정한다.

## D-014. 포지셔닝을 "뭐 먹을지" 중심으로 전환, 로드맵 재편 (2026-08-03)

**배경** 경쟁 분석 결과 시장은 ① 식단 기록형(냠냠, 1만+ DL — 재고·장보기 없음) ② 재고 관리형(밥타임 등) ③ 재고→레시피 추천형(냉장고파먹기 등) 3부류로 분절되어 있고, 순환 전체를 잇는 앱은 부재. 한편 "재고 관리 앱" 프레임은 1인가구向으로 읽히며, 주 타겟(주부)의 1차 고민은 "뭐 먹을지"라는 문제의식 제기.

**검토한 대안** — A 현행 유지 / B 타겟을 1인가구로 변경 / C 기능 유지 + 포지셔닝 전환 + 추천 조기화

**결정** — C.

- 포지셔닝: "냉장고 재고 관리" → **"내 냉장고 기준, 뭐 먹을지 해결"**. 기능 변경 없이 스토어 소개·온보딩 카피 차원.
- 로드맵 재편: **v1 = 임박 재료 기반 메뉴 추천 + 레시피 검색 등록** / v2 = AI 사진 인식(기존 v1) / v3 = 영수증 인식.
- 레시피 검색은 공공 조리식품 레시피 DB(COOKRCP01, 1,100여 건)를 **배치 적재 방식**으로 사용. 재료 자유 텍스트는 배치에서 파싱 후 D-007 패턴(제안→검증→등록)으로 마스터 매핑. 상세: `docs/dev/02-외부-API-검토.md`
- 기획서에 경쟁 서비스 분석 추가. MVP 범위는 불변(출시 우선).

**유보** — 시작 탭(D-012 냉장고)은 유지하되, "뭐 먹을지" 포지셔닝 기준으로 출시 후 데이터로 재검토.

## D-016. DB 스키마는 Flyway로 관리, 마스터 시드는 마이그레이션으로 (2026-08-03)

## D-017. 식재료 category는 마트형 13종 단층 구조로 확정 (2026-08-03)

**배경** ingredient.category 값 목록이 미결정 상태였다. 공공 영양성분DB의 4단계 학술 분류는 앱 UX에 과함.

**결정** — 마트 앱(SSG 등) 분류를 참고한 **13종 단층 값**으로 확정. 별도 코드 테이블 없이 `ingredient.category` 컬럼 값으로 사용.

- 마트 2단계 분류의 하위(사과, 배)는 category가 아니라 **식재료 개별 행**이 담당한다. 품종 단위는 커스텀 등록으로 흡수 (D-005).

**근거** — category 용도는 재고 필터·그룹핑뿐이라 단층으로 충분. 주 타겟(주부)에게 익숙한 건 마트 분류. 코드 테이블은 조인 비용만 늘리고 얻는 게 없어 확장 지점으로만 남긴다. 공공 코드 체계는 B2C 앱에 준수 의무가 없다.

## D-018. MVP 인증은 이메일+비밀번호(BCrypt) + JWT (2026-08-03)

**배경** app_user 인증 컬럼과 인증 방식이 미결정. 백엔드는 화면 없는 API 서버이므로 웹식 세션 방식은 부적합.

**검토한 대안** — A 세션(HttpSession) 기반: 모바일 앱과 부적합 / B JWT 토큰 / C 소셜 로그인 우선: 외부 연동 비용이 MVP에 과함

## D-028. 에러 응답 통일 — 401/403 구분과 내부 정보 비노출 (2026-08-20)

**배경** 인증 실패가 Security 기본 동작으로 403으로 나가고, 에러 본문 형식이 경로마다 제각각이며 서비스의 한국어 사유가 본문에 노출되지 않던 상태. Flutter 개발 직전에 정리.

**결정**

- **401 = 인증 안 됨**(토큰 없음·위조·만료, AuthenticationEntryPoint), **403 = 인증됐으나 권한 부족**(AccessDeniedHandler, 현재 미사용이나 자리 확보) — HTTP 의미론대로 구분
- 공통 에러 본문 `{ timestamp, status, error, message, path }` 로 전 경로 통일 (@RestControllerAdvice + Security 핸들러가 같은 ErrorResponse 공유 — 필터 단계 오류는 DispatcherServlet에 닿지 않아 Advice가 못 잡으므로)
- **500은 message를 "서버 오류가 발생했습니다"로 고정** — 예외 클래스명·메시지·스택을 응답에 절대 싣지 않는다(로그에만). 디버깅 편의를 위해 완화하고 싶은 유혹이 생기는 지점이지만, 내부 구조 노출은 공격 힌트가 되므로 완화하지 않는다
- SecurityConfig permitAll에서 /error 제거 — Advice가 응답을 직접 마감해 /error 디스패치가 사라졌고, 남겨두면 무인증 접근 가능 경로만 늘어남

**결과** — 15개 오류 케이스 회귀 통과. 인증 없는 요청은 경로 존재 여부보다 401이 먼저(D-022 비노출 원칙과 정합).
